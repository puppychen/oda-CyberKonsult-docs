# RFC-002：法規／知識類型必填與治理邊界

## TL;DR

每批上傳檔案在開始清洗前必須選擇一種「法規／知識類型」。一般知識、SOP、案例不啟用法規治理；法律、子法、ISO、NIST、CIS 才啟用法規切塊、品質檢查、版本與效期管理。

## 變更原因

既有畫面把「文件類型」標成必填，但整個法規元資料步驟可以略過，FastAPI 也未在建立清洗任務前驗證分類。這會讓同一份檔案在上傳、清洗、審核、入庫與法規版本頁被不同規則判斷，且 SOP 的畫面說明誤稱會啟用法規專用處理。

## 核准決策

| 決策 | 核准結果 |
|---|---|
| 新增一般類型 | 新增 `general`；新上傳不預選，管理者必須明確選擇。 |
| 相容類型 | `other` 保留 API 相容，但不顯示於新上傳與新建範本選單。 |
| 批次規則 | 一批檔案共用一種類型；混合類型必須分批上傳。 |
| SOP | 採一般知識處理，不啟用法規品質檢查與版本治理。 |
| 舊資料 | migration `011` 將既有 `NULL` 全部回填為 `general`。 |

## 完整行為矩陣

| 類型 | 新上傳可選 | 可開始清洗 | 法規切塊／品質檢查 | 版本／效期治理 |
|---|---:|---:|---:|---:|
| 未選擇 | 否 | 否 | 否 | 否 |
| `general` | 是 | 是 | 否 | 否 |
| `law`、`regulation` | 是 | 是 | 是 | 是 |
| `iso_standard`、`nist`、`cis` | 是 | 是 | 是 | 是 |
| `sop`、`case` | 是 | 是 | 否 | 否 |
| `other` | 否，僅相容舊資料 | 是 | 否 | 否 |

## 介面與 API

- Admin 步驟名稱與欄位名稱統一為「法規／知識分類」及「法規／知識類型」。
- 「一般知識文件」排列在選單第一項；未選擇時「套用並開始清洗」停用。
- `PATCH /api/v1/upload/{fileId}/metadata` 先逐檔套用分類；任一失敗不建立清洗任務。
- 清洗任務建立後，分類即鎖定；再變更類型會回傳 HTTP 409 與 `REGULATION_TYPE_LOCKED`。PATCH 與建立任務共用檔案列鎖，避免競態繞過法規治理。
- `POST /api/v1/clean` 為伺服器端最終防線；未分類時回傳 HTTP 400 與 `REGULATION_TYPE_REQUIRED`。
- 互動原型：[regulation-knowledge-type-required-mockup.html](../02-design/prototype/regulation-knowledge-type-required-mockup.html)。

## 資料遷移與回復

`011` 會先把受影響的 `files.id` 寫入 `migration_011_regulation_type_backfill`，再將同一批 `NULL` 更新為 `general`。降版時只把備援清單內且仍為 `general` 的資料還原為 `NULL`；migration 後改成其他類型的資料不會被覆寫。若管理者把資料重新指定為同值 `general`，技術上無法與原回填值區分，降版時仍會還原為 `NULL`。

**風險**：歷史 `NULL` 中可能包含實際法規，本次依核准決策一律視為一般知識。套用前必須備份 PostgreSQL；不重建 Qdrant，因為 `general` 與原本未分類資料的向量治理效果相同。

## 不變範圍

管理者帳號、資料清理規則、Maker-Checker 審查權限與既有 Admin 視覺風格不變。其他環境不由本次本機作業代為執行 migration。
