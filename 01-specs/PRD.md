## Epic 1：使用者認證與授權（FR-01）✅

### US-01-01：帳號密碼登入

> 身為**使用者**，我希望能夠使用帳號密碼登入系統，以便存取我有權使用的功能。

| AC 編號 | 驗收條件 |
|---------|----------|
| AC-01-01-01 | 支援 Email + 密碼登入，登入成功後回傳 JWT access token + refresh token |
| AC-01-01-02 | 登入失敗顯示「帳號或密碼錯誤」，不洩漏具體失敗原因 |
| AC-01-01-03 | 密碼錯誤超過 5 次鎖定帳號 15 分鐘，回傳 423 狀態碼 |
| AC-01-01-04 | 密碼符合資通安全「普」級政策：8 碼以上、含大小寫+數字+特殊字元、90 天過期、歷史 2 代不重複 |
| AC-01-01-05 | 密碼變更後 `tokenVersion` 遞增，所有既發 JWT access/refresh token 立即失效；後續憑舊 token 之請求一律回 401。實作見 `auth.service.ts changePassword()` + `JwtAuthGuard` 比對 token.tokenVersion 與 DB 當前值（fd20f53 修復；CLAUDE_LESSONS「Credential Rotation 事件窮舉」） |
| AC-01-01-06 | Access Token 效期為 60 分鐘；Refresh Token 效期維持 7 天。Access Token 過期時由前端自動刷新，不因使用者短暫停留或持續打字而直接清空畫面 |
| AC-01-01-07 | 每次登入依應用程式／裝置建立獨立工作階段；Admin、Cleaner、Chatbot 互不覆寫 Refresh Token，同一帳號最多保留 10 個有效工作階段 |
| AC-01-01-08 | Refresh Token 每次使用後原子輪替；舊 `jti` 重播時只撤銷對應工作階段。舊版 `users.refresh_token` 在第一次刷新時惰性轉換，不要求全體立即重新登入 |
| AC-01-01-09 | 新發 Access／Refresh Token 分別帶 `tokenUse=access`／`tokenUse=refresh`；Refresh Token 不可通過受保護端點的 Access 驗證。遷移期間僅相容未含 `tokenUse` 且未含 `jti` 的舊 Access Token |

### US-01-02：使用者帳號管理

> 身為**系統管理員**，我希望能夠管理使用者帳號，以便控制系統存取權限。

| AC 編號 | 驗收條件 |
|---------|----------|
| AC-01-02-01 | 可透過 Admin Dashboard 建立新使用者 |
| AC-01-02-02 | 可停用/啟用帳號，停用後使用者無法登入 |
| AC-01-02-03 | 可指派六種角色（basic_user / user / consultant / data_cleaner / data_reviewer / admin）；既有 it_user 併入 user |
| AC-01-02-04 | 角色變更後 refresh token 清除且 tokenVersion 遞增，舊 Token 立即失效 |

### US-01-03：安全登出

> 身為**使用者**，我希望能夠安全登出系統，以確保帳號安全。

| AC 編號 | 驗收條件 |
|---------|----------|
| AC-01-03-01 | 一般登出只撤銷目前工作階段；其他裝置或應用程式的工作階段仍可使用 |
| AC-01-03-02 | 「全部登出」撤銷該帳號所有工作階段並遞增 `tokenVersion` |
| AC-01-03-03 | Refresh 端點明確回傳 400／401 或本機無 Refresh Token 時，前端在原頁顯示重新登入視窗，不硬重載、不清除使用者正在查看的內容 |
| AC-01-03-04 | 網路錯誤、429、5xx、Refresh 回應格式異常或新 Access Token 重試後仍為 401 時，視為暫時性錯誤；保留 Token、頁面、對話與輸入內容並提供重試提示 |
| AC-01-03-05 | 同分頁並發請求共用一次 Refresh；跨分頁優先以 Web Locks 協調，fallback 使用多鍵競爭者互斥與可續期租約，等待者不得在租約有效期間自行刷新；執行前必須寫入 lease 並讀回確認 owner 為自己，否則移除 contender 後重新競爭。登入、重新驗證、SSO、密碼變更、登出與 Refresh 的 Token 寫入／清除共用同一互斥鎖。Refresh 必須帶 `X-ODA-Auth-Session-Protocol: 2`；API 以 426 拒絕未帶或版本不符的舊頁面，避免滾動更新期間舊程式參與 Token 輪替。Refresh 在 HTTP 回應與 JSON 解析完成後都必須重驗 Access、Refresh 與使用者快照；若帳號已切換，不得清除或覆寫新帳號 Token，並撤銷被捨棄回應建立的舊 Session |
| AC-01-03-06 | Chatbot 將未送出的草稿與目前對話 ID 保存於 `sessionStorage`，同頁重新登入後可延續操作 |
| AC-01-03-07 | 同頁重新登入鎖定原帳號且帳號欄唯讀；不同帳號不得取代原頁資料，且必須撤銷該次誤登入所建立的新工作階段。「稍後處理」後，重複背景 401 不得自行重開視窗，使用者仍可由提示列手動開啟 |

### US-02-05：分數過濾與品質保障

> 身為**系統**，需自動過濾低品質的檢索結果，確保回答品質。

| AC 編號 | 驗收條件 |
|---------|----------|
| AC-02-05-01 | hybrid 模式 RRF < 0.005 的結果**自動過濾移除**（過濾閾值；注意：與 AC-23-01-04 的 0.003 信心度判定閾值語意不同，見下註）|
| AC-02-05-02 | vector 模式 cosine < 0.3 的結果自動過濾移除 |
| AC-02-05-03 | RAG 結果不足時自動觸發 SearXNG 網路搜尋補充 |
| AC-02-05-04 | RAG 服務不可用時必須與「查無資料」分流，不得改用網路推測 |

> **閾值語意說明**（2026-04-18 補強）：系統有兩層不同閾值：
> 1. **過濾閾值**（AC-02-05）：`< 0.005`（RRF）或 `< 0.3`（cosine）→ 結果被**移除**。若過濾後無任何結果，保留 top 1 作為 fallback
> 2. **信心度判定閾值**（AC-23-01）：對過濾後留存的結果分級為 🟢/🟡/🔴，其中 🔴 低信心的 RRF 下界為 `< 0.003`
>
> 兩者不矛盾：0.003 僅會在過濾後 fallback 保留的 top 1 結果才可能觸發（否則早已在 0.005 被過濾）。實作見 `chat.service.ts filterLowScoreResults()` 與 `determineConfidenceLevel()`。
> 議題初判為 `non_cybersecurity` 或 `unclear` 時，top 1 fallback 不得當成「可恢復為資安回答」的有效證據；仍必須達到 AC-02-05-01／02 過濾門檻。

### US-02-06：非資安議題提醒

> 身為**使用者**，我希望系統辨識問題是否屬於資安範圍，以便理解 CyberKonsult 的服務邊界。

| AC 編號 | 驗收條件 |
|---------|----------|
| AC-02-06-01 | 資安問題不顯示範圍提醒，維持既有 RAG 與回答流程 |
| AC-02-06-02 | 混合問題顯示「包含非資安內容」提醒，且只回答資安相關部分 |
| AC-02-06-03 | 非資安初判仍先查 RAG；有達門檻的知識庫證據時依證據回答，否則才顯示服務範圍提醒，不回答一般內容 |
| AC-02-06-04 | 不明確初判仍先查 RAG；無有效證據時請使用者補充情境、風險或資訊系統 |
| AC-02-06-05 | 分類結果在即時串流與歷史對話中一致還原，三種回應層級共用相同規則 |
| AC-02-06-06 | `SGS`、`TUV`、`TAF`、`ODA` 等縮寫／機構片段無 RAG 證據時，可補上資安範圍詞執行網搜；回答必須由系統固定加上推測性前綴、低信心標示並提供來源；網頁正文與摘要皆空時不得視為證據 |
| AC-02-06-07 | 無任何證據的縮寫可在同一對話保留一輪；下一則資安限定詞會合併查詢，完整新問題不合併，且同一片段不得被併發請求重複消耗 |
| AC-02-06-08 | 回覆後的建議問題必須屬於資安、隱私、法遵或資訊風險；生成、驗證失敗或逾時時回傳可回覆的安全預設題 |

### US-02-07：重新產出與可靠重試

> 身為**使用者**，我希望在回覆不滿意或網路中斷時能安全重試，不會遺失完成回答、重複扣額或建立重複問答。

| AC 編號 | 驗收條件 |
|---------|----------|
| AC-02-07-01 | 只有目前對話最後一個已完成且屬資安／混合議題的回覆可重新產出；原問答保留，新問答追加於底部 |
| AC-02-07-02 | 同一次重新產出重試沿用 `regenerationAttemptId`，只計一次額度；完成結果直接回放 |
| AC-02-07-03 | 每次一般訊息送出使用獨立 `messageAttemptId`，同一次斷線重試必須沿用，且只建立一組問答、只計一次額度 |
| AC-02-07-04 | 回答已落盤但 SSE `done` 遺失時，前端依 attempt ID 復原完成回答；無法查詢伺服器狀態時不自行重送 |
| AC-02-07-05 | 相同 attempt 正在處理時拒絕重入；失敗或租約逾時可接手，舊處理程序不得覆寫新結果 |

| AC-20-01-03 | Cleaner 的來源資料、任務、審核與最近活動時間固定依 `Asia/Taipei` 顯示，不受使用者裝置時區影響 |
| AC-20-01-04 | 有多筆關聯任務時，以 `created_at DESC, id DESC` 決定最新任務；來源審核狀態依該任務工作流判定，不以逐檔 `review_status` 覆寫 |
| AC-20-01-05 | 同一篩選條件的 `total` 代表全部符合條件的資料數，不得只計算目前頁面；列表以 `uploaded_at DESC, id DESC` 穩定排序 |
| AC-20-01-06 | 來源列表在檔案名稱後顯示最新任務名稱；名稱、審核狀態與操作連結必須取自同一筆最新任務。舊任務未命名時顯示「任務 {ID 前 8 碼}」，無任務時顯示 `-` |

### US-20-02：刪除待審核來源資料

> 身為**系統管理員**，我希望在資料尚未批准或入庫前移除不應繼續審核的來源資料，同時保留既有歷程以供追溯。

| AC 編號 | 驗收條件 |
|---------|----------|
| AC-20-02-01 | 僅系統管理員可看見與執行刪除；資料清洗人員及審核人員不可操作 |
| AC-20-02-02 | 僅最新審核狀態為「未送審」或「待審核」，且所有關聯任務均未處理中、未批准、未入庫時可刪除；逐檔已標記「未通過」時須先由任務審核流程處理 |
| AC-20-02-03 | 執行前顯示關聯任務、刪除後有效檔案數、保留項目及阻擋原因；影響分析失敗時不得執行 |
| AC-20-02-04 | 知識庫存在同一來源切塊，或無法確認知識庫狀態時，採失敗關閉並禁止刪除 |
| AC-20-02-05 | 管理員必須填寫原因並輸入「刪除」後才能確認；後端再次驗證身分與最新狀態 |
| AC-20-02-06 | 刪除採邏輯刪除，保留原始檔、清洗產物、TaskFile、任務歷史與操作紀錄；預設來源列表不顯示，切換「已刪除」篩選後可查閱 |
| AC-20-02-07 | 所有關聯任務重新計算有效檔案統計；若任務已無有效檔案，任務轉為取消且不得審核或入庫 |
| AC-20-02-08 | 已刪除資料有任務關聯時只提供任務歷史入口；無任務時操作欄顯示 `-`，不提供刪除或審核操作 |

## Epic 17：RAG 信心度指示器（FR-23）✅

### US-23-01：信心度彩色標籤

> 身為**使用者**，我希望看到每則 AI 回覆的來源可信度標籤，以便判斷答案的可靠程度。

| AC 編號 | 驗收條件 |

## Epic 18：法規／知識分類治理（FR-24）✅

### US-24-01：上傳前完成法規／知識分類

> 身為**系統管理員**，我希望每批上傳檔案在清洗前具有明確分類，讓後續切塊、審查與版本治理採用一致規則。

| AC 編號 | 驗收條件 |
|---------|----------|
| AC-24-01-01 | 上傳完成後必須選擇「法規／知識類型」，未選擇時不得開始清洗 |
| AC-24-01-02 | 新上傳選單提供一般知識、法律、子法、ISO、NIST、CIS、SOP、案例，不提供相容用 `other` |
| AC-24-01-03 | 同批檔案共用一種類型；混合類型由管理者分批上傳 |
| AC-24-01-04 | 任一檔案套用分類失敗時，不建立清洗任務並保留表單內容供重試 |
| AC-24-01-05 | FastAPI 發現任一檔案未分類時回傳 HTTP 400 與 `REGULATION_TYPE_REQUIRED` |
| AC-24-01-06 | 只有法律、子法、ISO、NIST、CIS 啟用法規切塊、品質檢查、版本與效期治理 |
| AC-24-01-07 | 一般知識、SOP、案例與 `other` 採一般知識處理，不出現在法規版本與過期提醒 |
| AC-24-01-08 | 既有未分類檔案透過可回復的 migration 回填為 `general` |

> 變更決策與回復方式見 [RFC-002](./RFC-002.md)。
